# Radiology Copilot 的关键设计决策记录

> 一个面向影像科**诊教研一体化**的 AI 工作台原型
> 从需求定义到工程落地的完整记录

**免责声明**：本项目为科研教学原型，**没有医院合作、没有医生访谈、
没有真实用户使用数据**。文中所有结论均来自对公开资料的分析、
对公开数据集（BraTS 2020）的实验，以及构建过程中的观察。
凡未经验证的内容均明确标注。

---

## 1. 产品背景与用户痛点

### 1.1 问题背景

基于公开的影像科工作流资料，可以形成一个判断：
**影像科有三件重要的事，但它们今天由三套互不相通的工具承担。**

| 环节 | 现状 | 后果 |
| --- | --- | --- |
| 诊断辅助 | AI 分割工具与报告系统割裂 | 分割结果要手工搬运到报告，重复劳动 |
| 教学 | 学生看完片，缺少客观反馈 | "我画得准不准"没有答案，练习无法量化 |
| 科研 | 模型出错只留在日志里 | 想知道"模型在哪些病例上失败、失败成什么样"，只能靠印象 |

### 1.2 核心问题

不是"AI 分割不够准"，而是——

> **同一个病例的状态，在三套工具之间必然失真。**

医生在 A 工具里修正了掩膜，B 工具的教学案例里还是原始预测；
科研人员看到的失败案例，和临床上真正被修正过的病例对不上。
这种**状态割裂**才是真正阻止闭环形成的原因。

### 1.3 产品假设

> 如果把诊、教、研三个环节收敛到**同一个病例对象**上，
> 让影像、掩膜、测量值、审核状态始终指向同一条记录，
> 那么"模型在哪里出错"这件事就会自动沉淀为可复用的科研数据。

这个假设驱动了整个项目的架构决策。

## 2. 目标用户

| 用户 | 核心诉求 | 使用频率假设 |
| --- | --- | --- |
| **影像科医生** | 减少重复勾画与测量，快速产出可编辑报告 | 每次读片 |
| **医学影像学生 / 规培医师** | 用真实病例做有客观反馈的练习 | 教学周期内多次 |
| **医学影像 AI 科研人员** | 定位模型失败模式，形成改进任务 | 每个模型迭代周期 |

> ⚠️ 以上为基于公开资料的用户分析，**未经过真实用户访谈验证**。

---

## 3. 项目定位

**一句话**：把 AI 分割、结构化报告、教学练习与科研反馈串成一个围绕病例运转的闭环工作台。

**项目定位为**：
- ✅ 科研与教学原型
- ✅ 医学影像 AI + Agent 工具编排的**参考实现**
- ❌ **不是临床诊断系统**，未经临床验证

**第一版聚焦脑肿瘤 MRI**（BraTS 四序列：T1 / T1ce / T2 / FLAIR）。

---

## 4. 核心用户流程

```
①选择病例 → ②输入检查 → ③AI 分割 → ④确定性定量 → ⑤与参考标注比对
                │(不通过则阻止后续)
                ▼
        ⑥LLM Agent 工具调用 → ⑦报告草稿（待审核）→ ⑧人工确认审核 → 导出
                │
                ▼
        ⑨同一病例进入教学练习（答案提交前隐藏）→ 客观评分
                │
                ▼
        ⑩人工修正掩膜回流 → 差异分析 → ⑪科研反馈沉淀 → Dashboard / CSV
```

## 5. 功能优先级与 MVP 取舍

### 5.1 优先级排序

| 优先级 | 功能 | 理由 |
| --- | --- | --- |
| **P0** | 真实分割 + 确定性定量 | 没有真实数值，整个产品就是空壳 |
| **P0** | 输入合法性校验 | 几何不一致的掩膜会产生**看起来合理但错误**的数字，比报错更危险 |
| **P1** | LLM Agent 工具调用 | 这是与通用聊天机器人拉开差距的地方 |
| **P1** | 人工审核 + 版本保存 | 医疗场景下不能让 AI 自行定稿 |
| **P2** | 教学答案隔离 | 复用同一病例即可，实现成本低、价值明确 |
| **P2** | 科研反馈与修正回流 | 闭环的最后一环 |
| **P3** | 多平面 / 3D 阅片 | 锦上添花，不阻塞闭环验证 |

### 5.2 被排除的方案

| 方案 | 排除原因 |
| --- | --- |
| 多 Agent 框架 | 任务本身不需要；多 Agent 只会增加不可观测性 |
| 前后端分离 / 微服务 | 目标是 `python app.py` 一条命令可运行 |
| 在线掩膜涂抹编辑器 | 用 3D Slicer 改完上传即可，自研编辑器 ROI 太低 |
| 模型自动重训 | 本轮做的是"把错误变成数据"，不是自动训练 |
| 病理类型 / 分级推断 | **分割模型看不到组织病理，生成这类结论就是编造** |

### 5.3 关键取舍：刻意"不智能"的地方

这是本项目最核心的设计约束：

> **LLM 不参与任何数值计算，也不能自行触发分割或审批报告。**

理由：医学数值错一位就是事故。所以：

- 体积由 `体素数 × 体素体积` 确定性计算
- Dice 由确定性代码计算
- LLM 只负责**选工具、排顺序、写叙述**
- `run_segmentation` 即使模型传 `confirm=true` 也返回 `refused`——确认必须来自用户点击
- `generate_report_draft` 只能写 `pending_review`，**无法批准**

## 6. 人工审核与安全机制

| 机制 | 实现方式 |
| --- | --- |
| 报告审核 | 默认 `pending_review`；人工确认后新增修订版本，**不覆盖**原始预测 |
| 分割触发 | 仅用户点击界面按钮可触发，Agent 无法代办 |
| 来源区分 | AI 预测 / 数据集参考标注 / 人工修正三类掩膜分别存储、各自带标签 |
| 修正来源 | 用户上传标注为「用户上传的修正掩膜」；演示路径标注为「演示（由参考标注模拟）」 |
| 回答一致性 | LLM 回答中的体积与病例编号与工具**真实返回值**比对，不符时标注而非采信 |
| 参数校验 | 模型返回参数按 JSON Schema 校验，不合法回灌错误而非拼进 Python 调用 |
| 工具边界 | 无 shell / 文件读写 / 删除类工具 |
| 数据最小化 | 发送给 LLM 的只有结构化字段，**不含影像、路径、患者信息** |

## 8. 问题定位与迭代记录

以下均为**实际运行中发现并修复的**问题，按发现顺序记录。

### 8.1 影像显示问题

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| MRI 显示为一片白块 | 灰度窗按百分位计算时把背景 0 计入，去颅骨影像 85% 是背景，组织全被压到量程顶端 | 百分位只在非零体素上统计 |
| 阅片页大量黑色留白 | 按原始矩阵渲染，脑组织只占画面一小块 | 新增按非零体素投影的**正方形**裁剪框，面积降至 60% |
| 缩放时掩膜边缘发虚 | 影像与掩膜使用同一种插值 | 影像双线性、**掩膜强制最近邻**，标签不产生中间值 |

### 8.2 数据正确性问题（最严重的一类）

| 问题 | 后果 | 修复 |
| --- | --- | --- |
| 手写归一化语义错误 | **WT Dice 只有 0.397**（正确应为 0.925） | 对照 MONAI 源码后改为调用官方 transform |
| 同一病例重复统计 | 跑两次后 n=2、σ=0.000，让未验证的模型看起来"很稳定" | 按病例去重取最新一次 |
| 单样本显示 σ=0.000 | 读起来像"完全一致"，实为"无法测量" | 改为「样本量 1，标准差不适用」 |
| 标签约定字符串被误判为病例编号 | 正确的回答被一致性校验误报 | 收紧正则，要求数字段必填 |
| 体素体积 0.001 mL 被判为体积不符 | 正确引用被误报 | 改为递归扫描所有 mL 语义字段 |

### 8.3 流程与安全问题

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| **教学答案可被绕过** | 「显示参考标注」按钮无条件解锁，且前端隐藏不等于后端校验 | 新增后端权威校验 `reveal_allowed()`，所有渲染路径都走它 |
| Agent 工具摘要输出乱码 | 漏写调用括号，把 `<bound method ...>` 串喂给 LLM | 补括号 + 回归测试 |
| 函数调用探测不稳定 | 探测用 `tool_choice="auto"`，模型有权用散文回答 | 改为强制指定函数，确定性判定 |

### 8.4 这一轮的教训

> **"看起来能跑"和"真的正确"之间的差距，比想象中大得多。**

归一化问题最典型：代码没有任何报错，模型也输出了看起来合理的掩膜，
只是 Dice 从 0.92 掉到了 0.40。如果没有和官方实现对照，
这个错误会一直留在代码里。

**由此确立的原则**：
凡是关键的预处理与后处理，一律调用官方实现而不是凭文档手写；
凡是数值，都要有可对照的基准。

## 9. 效果评估

### 9.1 分割精度（真实测量）

6 例公开 BraTS 2020 病例，模型预测 vs 专家参考标注：

| 区域 | 平均 Dice | 标准差 |
| --- | ---: | ---: |
| WT | 0.8889 | 0.0604 |
| TC | 0.9243 | 0.0155 |
| ET | 0.8400 | 0.0327 |

与 MONAI 官方公布水平一致，说明**权重、通道顺序、预处理与后处理都正确落地**。

> ⚠️ **样本量仅 6 例，不构成对模型泛化能力的统计结论。**

### 9.2 Agent 执行（真实测量）

| 指标 | 值 |
| --- | ---: |
| 模型 | DeepSeek `deepseek-chat` |
| 工具调用 | 6 次 |
| 模型 API 往返 | 3 次 |
| 耗时 | 模型 4.42 s / 工具 0.32 s |
| 一致性校验 | 通过 |
| 报告叙述 token | 输入 579 / 输出 264 |

### 9.3 工程质量

- 311 个自动化测试全部通过
- 测试无需数据集与权重即可运行，且与宿主 `.env` 隔离（不会产生真实 API 调用）
- 关键安全属性（答案隔离、工具拒绝、参数校验、跨病例隔离）均有测试覆盖

## 10. 已知局限及后续计划

### 10.1 已知局限

| 局限 | 影响 |
| --- | --- |
| **无真实用户验证** | 所有用户价值判断均为假设，未经医生/学生/科研人员实测 |
| **模型未做外部验证** | 仅在 BraTS 2020 同源数据上验证，未做多中心测试 |
| **无临床金标准** | 教学模块只能给出与参考标注的一致性，不能评临床对错 |
| 仅轴位阅片 | 无多平面重建与 3D 重建 |
| 无在线掩膜编辑器 | 需借助 3D Slicer 等外部工具 |
| 切换病例约 5 秒 | 同步加载 4 个序列并做输入校验 |

### 10.2 后续优先级

1. **真实用户验证** —— 找 3–5 位影像科医生/学生做可用性测试，
   验证"状态割裂是真痛点"这个核心假设（这是当前最大的未验证风险）
2. **多中心数据验证** —— 在非 BraTS 来源的数据上测模型表现
3. **在线掩膜编辑** —— 学生在浏览器内直接勾画并即时评分
4. **纵向随访对比** —— 同一患者多时间点体积变化曲线
5. **多模型并列评测** —— 同一病例并行跑多个模型版本做误差对比

### 10.3 明确不做的

- 让 LLM 生成病理诊断或治疗建议
- 把 Dice 说成"诊断准确率"
- 把演示数据包装成真实临床结果
- 在没有任何真实用户反馈前，声称产品验证了用户价值

> 每一个数字都有可复现的来源，每一处未验证的地方都明确标注为未验证。
