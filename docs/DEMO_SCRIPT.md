# 版本 A · AI 产品经理（90 秒）

**重点：业务场景 → 用户需求 → 工作流 → 产品价值 → 评估**

### 0:00–0:12 ｜ 问题

> "这是 **Radiology Copilot**，一个影像科**诊教研一体化**工作台，第一版做脑肿瘤 MRI。
>
> 我调研后发现，影像科真正的痛点不是『AI 分割不够准』，
> 而是**同一个病例的状态在三套工具之间必然失真**——
> 医生在分割工具里改了掩膜，教学案例里还是原始预测，科研端对不上。"

**（指向首页四张能力卡）**
> "所以我把诊、教、研收敛到**同一个病例对象**上。"

### 0:12–0:32 ｜ 诊断辅助

**（切到「智能阅片」，指向 MRI 与彩色叠加）**

> "选病例后系统先做**输入检查**——序列是否齐全、几何是否一致。
> **不通过就阻止分割**，因为几何错位的掩膜会产生看起来合理但完全错误的数字。
>
> 点『运行 AI 分割』，跑的是 MONAI 官方 SegResNet 权重，
> 输出全肿瘤、肿瘤核心、强化肿瘤三个**嵌套**区域。
>
> **体积由确定性代码算**——体素数乘体素体积。**LLM 不参与任何数值计算**，这是刻意的。"

**（指向右侧测量面板）**
> "6 例公开数据实测，全肿瘤区平均 Dice **0.889**，和 MONAI 官方水平一致。
> 但我要说明：**只有 6 例，是小样本实验，不代表模型泛化性能。**"

### 0:32–0:52 ｜ 报告与审核

**（切到「AI 报告」，指向「推理模型」选择器）**

> "模型可以切换：默认 DeepSeek，秒级响应；也可以一键切成**本地 Qwen3-0.6B**——
> 462 MB、纯 CPU、**数据不出本机**。
>
> 这里有个我特意做的设计：**本地不可用时，系统不会自动改用 DeepSeek**。
> 把病例数据发到第三方，和在本机跑模型是两件不同的事，必须由我明确选择。"

**（输入"分析当前病例并生成报告草稿"）**

> "Agent 帮我调工具拿真实数据。看下面的执行记录——**6 次真实工具调用**，
> 每次都有状态和耗时，所以能证明工具**真的跑了**，而不只是模型描述了一遍。
>
> 报告默认是**待审核**，人工确认后才标记已审核，而且审核记录是**独立修订版本**，
> **不覆盖**原始模型预测——否则科研反馈就失去依据了。"

### 0:52–1:10 ｜ 教学闭环

**（切到「教学模式」，点「加载练习」）**

> "教学模块复用**同一个病例、同一份参考标注**。
> 关键约束是**提交前不泄露答案**——这一点有单元测试保证。
>
> **（点「显示参考标注」）** 未提交时点击会被拒绝：
> 『参考答案在提交前不可查看』。而且这不是前端隐藏，
> **后端也会二次校验**，改前端绕不过去。"

**（提交后指向反馈）**
> "提交后解锁，给出与参考标注的 Dice、体积差、漏分割和过度分割体素数。
> 只交文字的话给出**结构化核对清单**，并明确写清**这不是分数**；
> 涉及病理分级的，我明确标注不自动评分——**这个系统没有临床金标准，我不会假装能评临床对错。**"

### 1:10–1:30 ｜ 科研闭环与总结

**（切到「科研反馈」，指向 Dashboard 与修正历史）**

> "最后是科研端。两条规则很重要：
> **只聚合真实测量值**——没有参考标注的病例贡献为零，而不是贡献一个 0 分；
> **空是合法状态**，没数据就显示空状态。
>
> 这里还有**人工修正回流**：医生用 3D Slicer 改完掩膜上传，
> 系统校验尺寸、affine、方向、标签编码，给出与预测的差异分析，
> 保存为**独立修订版本**并沉淀成科研记录。
>
> **我的判断是**：这个产品里模型不是最难的部分，
> 真正决定它有没有用的是——数值可复现、来源可区分、
> **Agent 不做它不擅长的事**，以及**没有数据时如实说没有**。"

# 版本 B · Agent 产品经理（90 秒）

**重点：工具调用 → 状态管理 → 真实执行记录 → 人工审批 → 安全控制**

### 0:00–0:12 ｜ 定位

> "这是 **Radiology Copilot** 的 Agent 层。我做的核心判断是：
>
> **LLM 不负责分析影像，也不负责算数。**
>
> 影像分析交给经过验证的分割模型，数值计算交给确定性代码。
> Agent 只负责**选工具、排顺序、把结构化结果组织成回答**。"

### 0:12–0:35 ｜ 工具注册与真实执行

**（切到「AI 报告」，输入"分析当前病例，查询分割结果，整理体积并生成报告草稿"）**

> "这里有 9 个已注册工具，每个都有明确的 JSON Schema。
>
> **（指向执行记录）** 6 次真实工具调用：获取病例、输入检查、读分割结果、
> 算体积、查审核状态、生成报告草稿。每次都有**状态和毫秒级耗时**。
>
> 这是可核查的——**工具确实执行了**，而不是模型叙述了一遍。
>
> 模式标签写的是『LLM 工具调用模式（真实函数调用）』。
> 如果没配 API 或者端点不支持 function calling，
> 它会降级到固定工作流并**如实标注**，**不会假装调用成功**。"

### 0:35–0:55 ｜ 安全控制（这是我最想讲的部分）

> "我设计了四条安全边界：
>
> **第一，参数校验。** 模型返回的每个参数按 JSON Schema 校验——
> 类型、必需项、未声明属性、枚举值。不合法直接返回错误并把原因回灌给模型，
> **不会拼进 Python 调用**。
>
> **第二，不能自行改变状态。** 运行分割会消耗算力、改变系统状态，
> 所以 `run_segmentation` **即使模型自己传 `confirm=true` 也返回拒绝**——
> 确认必须来自用户点击按钮。
>
> **第三，不能审批报告。** `generate_report_draft` 只能写 `pending_review` 修订，
> 审批是人的动作，Agent 够不到。
>
> **第四，没有危险工具。** 注册表里没有 shell、没有文件读写、没有删除。"

### 0:55–1:15 ｜ 幻觉防护

> "还有一层是**回答一致性校验**：
> 模型回答里出现的每个体积（mL）和病例编号，
> 都会和工具**真实返回值**比对。
>
> 不一致的时候，我**不会用模型的说法覆盖工具结果**，
> 而是在回答旁边标注提示，让用户以工具结果为准。
>
> 提示词里也禁止它写 Dice 这类科研指标——那些属于算法评估，不属于影像报告。"

### 1:15–1:30 ｜ 真实性与收尾

> "最后说真实性。这套东西**真的跑通了**：
> DeepSeek `deepseek-chat`，3 次 API 往返、6 次工具调用、4.7 秒，
> 一致性校验通过，报告草稿 1062 字符待审核。
>
> 过程中我修掉了几个真实缺陷：探测用 `tool_choice="auto"` 导致不稳定、
> 正则把标签约定字符串误判成病例编号、工具摘要输出对象 repr。
>
> **我的体会是：Agent 产品的难点不在『让它能调用工具』，
> 而在『证明它调用了、限制它不能做什么、以及它说错话时你怎么办』。**"

### 主动说明的边界（体现判断力）

- **6 例是小样本**，不代表泛化性能
- **没有真实用户验证**，用户价值判断仍是假设
- 演示路径（用参考标注模拟修正）**明确标注为演示**
- 系统**不做**病理类型/分级推断——分割模型看不到组织病理
- 本地模型只做过 **3 个任务、1 个病例、1 次运行**的验证，**不能据此说它可靠**
  （见 [MODEL_COMPARISON.md](MODEL_COMPARISON.md)）

### 可能被问到的问题

| 问题 | 回答要点 |
| --- | --- |
| 为什么不用多 Agent？ | 任务本身不需要；多 Agent 只增加不可观测性。单 Agent + 工具注册表已覆盖需求 |
| 怎么保证 LLM 不编造数值？ | 数值全部由确定性代码算好原样填入；LLM 只写叙述，且提示词附的是结构化事实；事后还有一致性校验 |
| 为什么让 Agent 无法自己跑分割？ | 消耗算力、改变状态的操作必须由用户确认。即使模型传 `confirm=true` 也拒绝 |
| 标签编码为什么要显式声明？ | 同一个整数 `3` 在 BraTS 里不存在、在 MSD 里是强化肿瘤。猜错会让所有 Dice 失去意义 |
| 参考标注可靠吗？ | 参考标注本身有观察者间差异，所以界面写明"只反映与**特定**标注的一致性" |
| 最大的技术坑是什么？ | 归一化语义错误：手写 `(x-μ)/σ` 作用到整个体积，背景被推到 −4σ，**Dice 从 0.925 掉到 0.397**。教训是预处理必须调官方实现 |
| 怎么扩展到其他部位？ | `cases.py` 的适配器模式支持新增数据集（声明模态映射与标签约定），模型换成对应 MONAI bundle |
| 为什么默认用远程 API？ | 现场演示无法等本地 CPU 每轮 100–425 秒；本地模型保留为一键可切，用来展示轻量本地方案 |
| 本地模型慢多少？ | 正确性 3/3 持平，平均耗时 207.8s vs 4.7s，约 44×（本机 80 核被他人作业占满，纯 CPU） |
| 下一步做什么？ | **真实用户验证**——找 3–5 位医生/学生做可用性测试，验证"状态割裂是真痛点"这个核心假设 |
